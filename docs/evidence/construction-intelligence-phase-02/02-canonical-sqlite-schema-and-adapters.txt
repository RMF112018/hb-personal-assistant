Phase 02 — Prompt 02 — Canonical SQLite Schema and Adapters

1. Summary
----------

Lands the Phase 02 canonical construction-index SQLite schema as a single V5
migration (additive only — V1-V4 tables remain untouched) plus a matching
Python adapter layer on `ConstructionStore`. The compatibility bridge installed
by Prompt 01 at the model layer now extends into SQLite: callers can write
canonical source_id-keyed records into the new tables while the legacy
source_key plumbing in V2-V4 keeps serving the unmigrated downstream code.

Ten new tables:

  - construction_source_locations              (canonical replacement for V2
                                                construction_source_resolutions)
  - construction_source_sync_state             (canonical replacement for V2
                                                construction_delta_tokens)
  - construction_source_crawl_runs             (canonical replacement for V2
                                                construction_crawl_receipts)
  - construction_drive_items                   (canonical replacement for V2
                                                construction_drive_item_inventory,
                                                enriched with project_number_detected,
                                                document_type_detected,
                                                indexing_policy, classification_status)
  - construction_project_identity              (new — project master)
  - construction_project_source_matches        (new — n:n project↔source binding)
  - construction_document_cards                (new — document discovery workflow)
  - construction_processing_receipts           (new — operation audit log,
                                                distinct from crawl receipts)
  - construction_sync_errors                   (new — error history)
  - construction_email_intelligence_deferred_state
                                               (new — singleton permissions guard;
                                                hard CHECKs lock mailbox writeback
                                                and full-body persistence to 0)

Four supporting indexes on hot paths (project_key, project_number_detected,
(source_id, last_modified_datetime), review_required).

Adapter coverage on `ConstructionStore` (defense-in-depth alongside SQL CHECKs):

  - upsert_source_location raises if read_only is anything but True.
  - set_email_intelligence_deferred_state raises if mailbox_writeback_allowed
    or persist_full_body is True.
  - All boolean fields normalized 1/0 ↔ True/False at the adapter boundary.
  - JSON columns (baseline_policy_json, folder_policies_json, detail_json)
    accept dicts in / return dicts out via json.dumps/loads with sort_keys=True.

No CLI surface change. No data migration from V2 inventory rows into the
canonical drive_items table — that lands in a later prompt once downstream
callers (graph resolver, manifests, classifier, fixtures) move off Phase 01
source_key plumbing.

7. Guardrail Attestation
------------------------

  - External systems remain read-only. The new
    construction_source_locations.read_only column is CHECK(read_only = 1) at
    the schema level, blocked at the adapter level, and was never relaxed
    from Prompt 01's `SourceLocation.read_only: Literal[True]`.
  - No source-document copies into Obsidian. The canonical
    construction_drive_items table has no body / content / text / excerpt /
    full_text columns — verified by test_no_body_or_text_columns_in_drive_items.
  - No full-document text in vault notes. The
    construction_email_intelligence_deferred_state.persist_full_body column
    is CHECK = 0 and rejected by the adapter.
  - No deletion / movement / overwrite / rename of source files. All adapters
    insert or upsert; the only delete operation is the soft-delete deleted=1
    toggle on construction_drive_items, which mutates the index row, not the
    source file.
  - No production webhooks.
  - No company-wide rollout.
  - Sensitive records route to review. The
    construction_project_source_matches.review_required boolean and the
    construction_document_cards.needs_review boolean (default 1) carry the
    routing signal.
  - Models execute no file operations and never override controller
    validation. The canonical schema offers no path for either.
  - Mail.ReadWrite.All read-only enforcement: the
    construction_email_intelligence_deferred_state.mailbox_writeback_allowed
    column is CHECK = 0 and rejected by the adapter. Adapter-level error
    message: "mailbox_writeback_allowed must be False — Phase 02 mailbox
    stays read-only even when Mail.ReadWrite.All is granted".

  Stop conditions honored:
    - No column collisions with V1-V4 tables (all new table names).
    - No external-system writeback path introduced.
    - No mailbox mutation path.
