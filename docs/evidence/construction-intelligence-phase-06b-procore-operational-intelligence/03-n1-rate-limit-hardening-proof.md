## 1. Problem and fix

The financial N+1 fan-out in `live_sync.py` issued **one child GET per parent** with the
parent list unbounded — the only existing bound was a *record* cap (`len(child_records) >=
max_items`), not a *request* cap. A project with many parents drove an unbounded number of
child GETs (rate-limit / long-run risk), and the fan-out was invisible in the receipt.

**Fix:**
- Module const `DEFAULT_MAX_CHILD_REQUESTS = 50`; new `max_child_requests` param on
  `run_live_sync` and `--max-child-requests` (default 50, `min=1`) on `procore live sync`.
- The N+1 loop now caps the number of child GETs. When `child_request_count` reaches the cap,
  it sets `cap_reached`, counts the remaining parents as skipped, and stops fanning out.
- Per-parent fetch errors still increment an error count + append a redacted entry to
  `redacted_errors` and **continue** (continue-on-child-error preserved); the record cap is
  preserved.

## 2. Receipt fields (additive `n1_fanout` block)

`_build_receipt` gained an additive `n1_fanout` key (None for non-N+1 endpoints), carrying the
five required fields plus the cap value:

```json
"n1_fanout": { "is_n1": true, "parent_count": 5, "child_request_count": 2,
               "child_skipped_count": 3, "child_error_count": 0,
               "cap": 50, "cap_reached": true }
```

When the cap fires, `reason_codes` gains `n1_child_cap_reached` (informational; does not by
itself flip state — partial_success is still driven by child errors as before).

---

## 3. Idempotency / linkage preservation (stop condition)

The stop condition is *"child cap changes break idempotency or parent/child linkage."* The cap
only limits **how many parents are fanned over** this run; the children that are fetched upsert
identically (idempotent by `procore_record_id`) and keep their `parent_procore_id` linkage. A
later run (or a higher cap) backfills the rest without duplicates. **Proven** by
`test_capped_run_is_idempotent_and_preserves_linkage` and scenario A of the evidence JSON:
running a capped sync twice yields identical SQLite record ids and row count, with intact
parent linkage. The stop condition is **not** triggered.

The cap touches no upsert key, normalizer, `path_template`, contract, or held endpoint, and
the dry-run orchestrator (`sync.py`, no network I/O) is unaffected. The HTTP paginator's
existing 429/Retry-After exponential backoff (5 retries, 1–60s, jitter) is unchanged — the cap
layers on top as a fan-out/long-run bound.
