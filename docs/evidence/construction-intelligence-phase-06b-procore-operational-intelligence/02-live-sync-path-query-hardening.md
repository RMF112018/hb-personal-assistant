## 1. Defects found and fixed

### Defect A — top-level query param tested the substituted path (the package's named bug)
The top-level query-param guard read `if "{project_id}" not in path:`, where `path` is the
**resolved** path (`_resolve_path` / the parent-template branch already substituted
`{project_id}`). The literal placeholder is therefore *always* gone, so the guard was
**always true** → every path-scoped top-level endpoint (rfis, submittals, observations,
schedules, …) received a **redundant `?project_id=`** query param. The documented intent
(and the already-correct N+1 child guard, which tested `adapter.path_template`) is:
project_id as a query param **only when it is not a path segment**.

**Fix:** the decision now keys off the originating template via the pure helper
`_project_id_query_params(path_template_used, …)`, where `path_template_used` is the
`parent_path_template` (N+1 parent fetch / meeting-detail / activities) or the
`path_template`. Flat lists keep project_id as a query param; path-scoped and v2.0
company/project endpoints carry it in the path.

### Defect B — inline-child records stored a placeholder template as their source URL
Inline-extracted children (rfi-responses / submittal-responses / meeting-topics, pulled from
the parent payload) wrote `source_url_redacted=redact_source_url(child_adapter.path_template)`
— i.e. a template with literal `{project_id}`/`{rfi_id}`, not a real path.

**Fix:** store the **resolved** child path:
`redact_source_url(_resolve_child_path(child_adapter, procore_project_id, record_id))`
(`record_id` = the parent's procore id, in scope). The financial N+1 loop is unaffected — its
children flow through the normalizer's `source_url`.

### Helpers extracted (pure, testable)
`_project_id_query_params`, `_child_query_params` (encapsulates the template-correct child
logic + `_N1_CHILD_EXTRA_PARENT_PARAMS` rfq `contract_id`), `_api_version`,
`_request_classification`. `_resolve_path` / `_resolve_child_path` were already correct and
are unchanged.

## 2. Receipt redacted request classification (required-work item 4)

`_build_receipt` now emits an additive, secret-free `request_classification` derived from the
endpoint template only — no resolved ids, tokens, query values, or bodies:

```json
{ "api_version": "v2.0", "path_scope": "company_project",
  "project_id_param": "path", "n_plus_1": false,
  "path_template_redacted": "/rest/v2.0/companies/{company_id}/projects/{project_id}/schedules" }
```

The receipt already recorded only `http_method`+counts (no raw URL/query), and the redaction
layer (`redact_request`, `redact_source_url`) strips query strings; this makes the redacted
request classification explicit.
